# VipineshkaVPN / SecureConnect — пять «почему» и проверяемый план исправлений
Дата: 2026-10-30. Сеть: российская мобильная сеть по сообщению владельца; Android 16, Xiaomi 2607APCA5G; Xray 26.9.30.

## Входные факты (из пользовательской диагностики)
- `VPN state: Connected`, `VPN service/TUN live: true/true`; это доказывает наличие сессии, **не конец-в-конец интернет**.
- `SOCKS CONNECT 41 ms`, но `www.gstatic.com:tls=timeout` и `cp.cloudflare.com:tls=timeout`, IO 5000 ms. SOCKS CONNECT не равен успешному TLS/HTTP.
- `Verified pool ready 0/21`; `saved working history 0/60`; YouTube подтверждений 0, двойных проверок скорости 0.
- PSS=441 MB, сканер сообщает о памяти; ресурсный soft-limit=384 MB.
- 240 кандидатов в каталоге, 54 облачных HTTPS результатов, но только один совпавший по fingerprint локальный кандидат.
- Скорость последнего теста 2,84 Мбит/с; требуемые для метки видео >=5/1 Мбит/с; нет достоверного сравнения с прямой сетью.
- 13 установленных российских приложений настроены в EXCLUDE_SELECTED на прямое соединение без VPN.

## Проблема 1: 0/21 — пять почему
1. Нет подтверждённых резервов: локальная история пуста.
2. Отдельный сканер требует HTTPS + страницу YouTube + два теста 5/1, а не только рабочий интернет.
3. Непрохождение YouTube/скорости исключает узел из 720p-пула, даже если общая HTTPS-доступность есть.
4. Ресурсный регулятор останавливает сканирование при PSS>=384 MB; на телефоне 441 MB.
5. Не разделены продуктовые классы «рабочий безопасный маршрут» и «видео >=720p», а диагностика не показывает численность промежуточных классов.
Статус: подтверждены требования допуска и soft memory gate в коде. Исправление умеренного нулевого резерва уже в ветке; нужно отдельно реализовать HTTPS-only fallback **не помечая его видео-проверенным**.

## Проблема 2: TLS-тайм-ауты — пять почему
1. Проверка SOCKS открыла удалённое соединение, затем TLS не ответил за 5 с.
2. Это может быть фильтрация конкретного сайта, плохой маршрут/транспорт или сервер.
3. Изначально приложение проверяет только gstatic и Cloudflare; обе проверки могут быть ограничены независимо от работоспособности других адресов.
4. Программный health checker объединяет отказ контрольного сайта и отказ VPN-сервера в одинаковое пользовательское сообщение.
5. Нет третьего независимого валидированного HTTPS источника и отдельного диагноза по стадиям.
Изменение: в ветке добавлен только один **ограниченный** HTTPS-повтор через Xray SOCKS к www.apple.com, если удалённый SOCKS CONNECT уже прошёл, но прежние проверки сорвались в TLS/HTTP. Сертификат и hostname проверяются; системный TUN по-прежнему не доказан.

## Проблема 3: память 441 MB — пять почему
1. Память превысила soft PSS и сканер остановился.
2. Xray — native/Go + Kotlin; PSS не равен объёму Java heap и не объясняет источник нагрузки.
3. Повторные TLS-долгоживущие соединения и XHTTP могут увеличивать PSS, особенно при плохой сети.
4. Для Xray-core 26.9.x существует публичный отчёт о XHTTP/HTTP2 параллельных зависших handshake, issue #6797.
5. В текущей диагностике **нет счётчиков Go goroutines/числа сокетов**, поэтому причинность не подтверждена.
Следующий опыт: измерить PSS и сокеты под XHTTP vs RAW на одном разрешённом тестовом сервере; контроль параллелизма, версия Xray/Go, без немотивированной смены native AAR.
Источник: https://github.com/XTLS/Xray-core/issues/6797

## Проблема 4: белый список оператора — пять почему
1. Нужный VPN-сервер может быть недоступен из мобильной сети.
2. Ограничения могут действовать по адресу/порту/протоколу, не только HTTP Host/SNI.
3. Название VK в заголовке не делает чужой IP адресом VK.
4. Бесплатные публичные узлы часто меняются, а GitHub Actions проверяет их из иной сети.
5. Нет гарантированно достижимого из данной SIM оператора доверенного VPN-шлюза.
Заключение: ни fingerprint, ни HTTP-BUG не дают общего обхода. Нужны проверка реальной сети/доступности и разрешённого шлюза; если маршрут закрыт, честное сообщение об отказе. Не публиковать «ускорение 3x» без измерений.

## Проблема 5: низкая скорость — пять почему
1. Один измеренный маршрут дал 2.84 Мбит/с.
2. Нет подтверждённо более быстрого локального резерва.
3. Загрузка узла, задержки, качество мобильной радиосети и блокировки отличаются.
4. Двойной тест скорости используется как порог допуска в 720p-пул, но не автоматическая оптимизация всех работоспособных узлов.
5. Нет согласованных повторных A/B измерений прямого и VPN-пути на одной SIM в одинаковый период.
Решение: ограниченный по трафику замер реальной скорости на устройстве и выбор максимальной медианной скорости среди безопасных и реально подключаемых маршрутов; «2–3 раза» — только если подтверждено.

## Проблема 6: «Connected» против настоящего интернета
1. Xray и TUN присутствуют.
2. SOCKS_CONNECT может пройти раньше TLS и HTTPS.
3. Проверка из UID VPN исключена из TUN (во избежание loop), поэтому проверяет proxy outbound, не всю маршрутизацию других UID.
4. Приложение имеет bypass для российских приложений (13 из них установлено): это прямой трафик по выбору настроек.
5. Не проверен контрольный пользовательский трафик из приложения, реально идущего через TUN.
Решение: разделить «туннель поднят», «прокси переносит HTTPS», «настройка TUN проверена»; не помечать через-VPN трафиком исключённые приложения.

## Протокол приёмки
1. CI: сборка + unit tests + lint + security audit.
2. На Xiaomi: через мобильную сеть проверить по стадиям SOCKS, DNS, TLS, HTTPS в Xray и отдельно системный TUN; открыть реальные сайты.
3. После STOP всё выключено, при Kill Switch утечки не допускаются; проверить IPv6 и DNS.
4. Измерить скорость без VPN / со стабильным VPN 3+ раз при одинаковых условиях.
5. Записать оператор, тип сети, дату и ошибку без публикации секретов конфигурации.
6. Только затем считать цель для конкретной российской SIM решённой.
