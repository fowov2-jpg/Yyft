# VipineshkaVPN: исследования мобильных ограничений в России — 30.10.2026

Статус: инженерная гипотеза на основе публичной документации и отдельных наблюдений пользователей. Это **не проверка на мобильных операторах из Android APK**. Цель: без ложного статуса VPN и без обещаний «в 2–3 раза».

## Что уже умеет действующий Android-код
- Исходник: `android/source.zip`, `app/src/main/java/com/secureconnect/app/vpn/XrayConfigBuilder.kt`.
- Поддержаны VLESS, VMess, Trojan, Shadowsocks, Hysteria2; клиентские транспорты RAW/TCP, WebSocket, gRPC, HTTPUpgrade и XHTTP (по совместимым ссылкам).
- REALITY ограничен RAW, XHTTP, gRPC. Для TLS/REALITY `fingerprint = q("fp") ?: "chrome"`. Нужно проверить качество default-фингерпринта в реальной российской сети; менять по умолчанию всем клиентам без измерений нельзя.
- Публичный `feed.json` из GitHub — **только внешний рейтинг**; локальный LTE/5G доступ он не подтверждает.
- Сервисные проверки, счётчик квалифицированных маршрутов и доказательство полезного трафика через TUN — отдельные стадии. При нулевом резерве разобраться с каждой стадией, а не присваивать «прошёл» по облаку.

## Выводы из публичных обсуждений
1. 4PDA, VPS-тема: один пользователь сообщил, что комбинация VLESS/REALITY/XHTTP работала с конкретным именем в операторском whitelist, тогда как другие имена не сработали. Никакой гарантии для МТС, МегаФон, билайн и t2 из этого нет.
   https://4pda.to/forum/index.php?showtopic=1094247&st=580
2. Xray GitHub: пользователи описывают проблемы разных uTLS-фингерпринтов на российских мобильных сетях. Отдельный комментарий сообщает, что `firefox` восстановил соединение для его сборки Xray в октябре; также есть issue про несовместимость некоторых вариантов с REALITY на более новых версиях ядра. Отпечаток — диагностируемый параметр, а не универсальная «волшебная» настройка.
   https://github.com/XTLS/Xray-core/discussions/7144
   https://github.com/XTLS/Xray-core/issues/7259
   https://github.com/XTLS/Xray-core/discussions/6785
3. Автор обсуждаемой схемы на Хабре **отозвал** своё предположение о том, что вся Yandex Cloud разрешена whitelist: автономные системы Yandex Cloud и Яндекса различаются; VM могут блокироваться. Не считать облачный VPS доступным только по бренду хостера.
   https://habr.com/ru/articles/1021160/
4. Официальная документация Xray: REALITY поддерживается с RAW/XHTTP/gRPC, настройка транспорта согласуется с сервером. Автоматически переключать XHTTP вместо RAW на чужой узел без поддержки сервера **нельзя**.
   https://xtls.github.io/en/config/transport.html
5. Официальная FAQ Amnezia: self-hosted не имеет универсального поддерживаемого решения whitelist; доступность зависит от оператора и региона, скорость следует мерить при одинаковом направлении теста.
   https://docs.amnezia.org/ru/faq/
6. GitHub issue: XHTTP/REALITY иногда показывают установленный TLS/пинг, но через туннель не идёт полезный трафик. Поэтому критична проверка HTTPS загрузки через TUN, а не `isConnected`.
   https://github.com/XTLS/Xray-core/issues/6482

## План для реальной реализации на телефоне
1. Отдельно установить тип сетевого отказа: `DNS`, `TCP connect`, `TLS handshake`, `Xray tunnel up`, `HTTPS response through TUN`, `download/upload bitrate`. Не делать вывод «whitelist» по одному тайм-ауту.
2. По **уже существующим разрешённым конфигурациям узлов** проверить совместимые сервером варианты TLS-фингерпринтов в ограниченном числе попыток, например `chrome` / `firefox`, когда совместимость ядра подтверждена. Нельзя отключать проверку сертификатов и нельзя считать SNI от чужого сайта доказательством whitelist.
3. Разделить «проба» и «подключение»: тестировать полезную загрузку и DNS через реальный туннель; прежнюю рабочую сессию сохранять пока безопасно. Не показывать «Защищено» только из-за установленного TUN.
4. Сортировка: сначала безопасный и доступный маршрут из реальной сети смартфона, затем меньшая задержка, выше **измеренная** скорость, меньше обрывов, меньше расхода батареи.
5. Для whitelist готовить отдельный **действительно достижимый доверенный шлюз**, если разрешён оператором. Никакой гарантии, что VPS с названием VK/Yandex пройдёт фильтры. Правила маршрутизации для российских приложений не равны обходу whitelist.
6. А/Б-протокол испытаний: один телефон, один оператор и один тип сети, одинаковый тестовый ресурс и период, исходные показания без VPN / через VPN, минимум несколько повторов. Измерения нельзя подменять данными GitHub runner. Не обещать множитель скорости.
7. Учитывать согласие пользователя на замеры, лимит объёма данных и число попыток. Секреты конфигураций не выгружать на GitHub.

## Доказательства завершения
- Результаты `assembleDebug`, unit tests, lint, security audit.
- На устройстве с российской SIM: запись маршрута и полноценного HTTPS-трафика через туннель, отсутствие утечек DNS и IPv6, STOP и onTaskRemoved, поведение при потере сети.
- Если проходящего whitelist маршрута в данной сети нет, приложение должно честно сообщать «не найден», а не подделывать трафик VK.

Это исследование оформлено для ветки `feature/vipineshka-russia-one-tap-20261030`; оно само по себе не меняет сетевое поведение текущего APK.
